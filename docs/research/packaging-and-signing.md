## 1. Tauri v2 on Windows

### 1.1 Bundling targets

Tauri v2 ships two native Windows installer targets, configured under `bundle.targets` in `tauri.conf.json`:

- **MSI (WiX)** — a Windows Installer package. Generated via the WiX Toolset, which `tauri build` downloads and invokes automatically if not already present. Set `"targets": ["msi"]`.
- **NSIS** — a `-setup.exe` installer built with the Nullsoft Scriptable Install System. Set `"targets": ["nsis"]`.

Both can be built simultaneously: `"targets": ["msi", "nsis"]`.

Sources:
- Tauri v2 docs, "Windows Installer" page, updated 2026-09-03 (`https://v2.tauri.app/distribute/windows-installer/`)

#### The Inno Setup gap

Tauri does not currently support Inno Setup as a first-class target. A feature request exists: GitHub `tauri-apps/tauri#16080` (2026-09-22). If Inno Setup is required, you must sign the generated executable externally.

#### Known NSIS issue — reinstall does not replace sidecar binaries

GitHub `tauri-apps/tauri#15134` (2026-03-21) documents that NSIS installers generated by Tauri do not replace `externalBin` sidecar executables on reinstall. The NSIS script references the correct binary path, but the bundler resolves the binary path before NSIS runs, and the reinstall path does not detect or overwrite an existing sidecar. **This means sidecar binary updates can silently fail on NSIS reinstall.** The MSI target does not appear to have this issue. Mitigation: use MSI for distribution, or add a custom NSIS uninstall/reinstall hook.

#### WiX FIPS compliance

If the MSI must be FIPS-compliant, set the environment variable `TAURI_BUNDLER_WIX_FIPS_COMPLIANT=true` before `tauri build`. Source: Tauri v2 docs ("Windows Installer").

### 1.2 Code-signing configuration

Tauri v2 supports code signing through `tauri.conf.json`, under `bundle.windows`:

```json
{
  "bundle": {
    "windows": {
      "certificateThumbprint": "A1B1A2B2A3B3A4B4A5B5A6B6A7B7A8B8A9B9A0B0",
      "digestAlgorithm": "sha256",
      "timestampUrl": "http://timestamp.digicert.com"
    }
  }
}
```

- `certificateThumbprint` — SHA1 or SHA256 thumbprint of the installed certificate in the local machine store.
- `digestAlgorithm` — must be `sha256`.
- `timestampUrl` — RFC 3161 timestamp server URL (e.g., `http://timestamp.digicert.com` or `http://timestamp.sectigo.com`). Timestamping ensures the signature remains valid after the signing certificate expires.

**Required field:** you must also set `bundle.publisher` in `tauri.conf.json`. Without it, signing silently fails. Source: Tauri community discussion #5739 (2026-04-05).

Tauri also supports **Azure Artifact Signing** directly, covered in section 3.

The signing step runs automatically during `tauri build` when `certificateThumbprint` is set. It calls the Windows SDK `signtool.exe` internally. Source: Tauri v2 docs, "Windows Code Signing" page, updated 2026-09-11 (`https://v2.tauri.app/distribute/sign/windows/`).

The build also generates a `.wix` or `.nsi` script that bundles the signature into the installer — Tauri does both the binary signing and the installer signing in one pass.

#### What actually breaks in practice

1. **Missing publisher field** — signing fails silently; the build completes but the MSI/NSIS output is unsigned. You only notice when validating it. Add `bundle.publisher` on every build.
2. **Certificate not in the machine store** — `certificateThumbprint` must match a certificate present in the Windows certificate store (CurrentUser or LocalMachine). CI runners often lack this and need `certutil` or Azure Key Vault integration.
3. **Timestamp server unreachable in CI** — some CI environments restrict outbound HTTP to port 443; the older timestamp servers listen on port 80. Use an HTTPS timestamp URL (`http://timestamp.digicert.com` works over port 80; some teams report needing `https://timestamp.digicert.com` instead).

### 1.3 The built-in updater (`tauri-plugin-updater`)

Tauri v2 provides an updater as a first-party plugin at `https://v2.tauri.app/plugin/updater/`.

**How it works:**
- Configure in `tauri.conf.json` under `plugins.updater` with a `pubkey` (ed25519 public key) and an `endpoint` URL that serves an update manifest.
- The update manifest is a JSON file with fields `version`, `url`, and `signature`. The `signature` is a base64-encoded ed25519 signature of the update archive, created with the corresponding private key at build time.
- On startup or on explicit check, Tauri fetches the manifest, verifies the signature against the bundled pubkey, downloads the update archive, verifies again, and applies it.

**Three server options:**
1. **Static JSON file** — host the JSON manifest on any static server (GitHub Pages, CDN). The simplest.
2. **Dynamic update server** — a custom backend. Tauri recommends CrabNebula Cloud as a turnkey managed server.
3. **CrabNebula Cloud** — official Tauri partner, managed service, handles distribution and signature management.

**Windows install modes** (configured via `installMode`):
- `installMode: "passive"` — NSIS runs with a progress bar but no user interaction. Best for silent updates.
- `installMode: "basicUi"` — minimal NSIS UI.

**Key constraint:** the updater plugin is for **side-loaded builds** (MSI/NSIS). For Microsoft Store builds, updates are handled by the Store and the updater plugin should be disabled or removed. Running both causes conflicts.

**What breaks in practice:**
1. **Signing keypair generation is manual.** `tauri sign` generates a keypair in a file on disk and prints a `TAURI_UPDATER_PUBKEY` and a corresponding private key. If the private key is lost, no updates can be signed. Store it in a password manager or CI secret, not just on one machine.
2. **The pubkey must match at build time.** If you regenerate the keypair and rebuild, old installs cannot verify the new update manifest until they are manually replaced.
3. **MSI updates via the updater are less tested than NSIS.** The Tauri community reports that the updater for MSI targets does not always replace running files cleanly (GitHub issues on the tauri repo). Test this explicitly in Phase 2 (feasibility spike) of the build plan.

### 1.4 Sidecar support

Tauri v2 supports bundling external binaries as **sidecars** — executables that are packaged inside the installer and placed alongside the Tauri binary. Configured via `bundle.externalBin`:

```json
{
  "bundle": {
    "externalBin": ["binaries/node-sidecar"]
  }
}
```

The actual binary must be placed at `src-tauri/binaries/node-sidecar-x86_64-pc-windows-msvc.exe` (target-triple suffixed). Tauri renames it to `node-sidecar.exe` during build.

The sidecar is launched from Rust via `tauri_plugin_shell`. Example from a community guide (Dev.to, 2026-07-05):

```rust
use tauri_plugin_shell::{ShellExt, process::CommandEvent};

#[tauri::command]
async fn start_sidecar(app: tauri::AppHandle) -> Result<(), String> {
    let sidecar = app.shell().sidecar("node-sidecar")
        .map_err(|e| e.to_string())?;
    let (mut rx, child) = sidecar
        .args(["--port", "3456"])
        .spawn()
        .map_err(|e| e.to_string())?;
    // store child handle for lifecycle management
    app.state::<Mutex<Option<CommandChild>>>().lock().unwrap().replace(child);
    // read stdout/stderr in background
    tauri::async_runtime::spawn(async move {
        while let Some(event) = rx.recv().await {
            // handle events
        }
    });
    Ok(())
}
```

Tauri's official Node.js sidecar guide (`https://v2.tauri.app/learn/sidecar-nodejs/`) recommends using `pkg` (yao-pkg/pkg) to compile the Node application into a standalone binary. For the Capybaras case, a **portable Node runtime** is preferred over pkg, because OpenClaw's Gateway has 65 direct dependencies with dynamic loading. pkg handles static require graphs well and dynamic graphs poorly. The alternative — shipping the portable Node runtime as a resource and running `.js` files — is also documented by Tauri, but ships readable JS and a larger runtime.

**Lifecycle management gap:** There is no official Tauri sidecar lifecycle management plugin. A feature request exists (`tauri-apps/plugins-workspace#3062`, 2025-10-23) for spawning, monitoring, health checks, auto-restart, and graceful shutdown. For now, this must be implemented manually in Rust code — spawn on app start, track child process handles, implement crash detection, and kill on app exit.

## 2. Microsoft Store submission

### 2.1 Developer account cost

**As of May 2026, the Microsoft Store developer account is FREE for both individuals and companies.**

- Individual developer registration was made free in late 2025.
- Company registration was made free in May 2026 (announced at `blogs.windows.com/windowsdeveloper/2026/05/07/`).

Prior to these changes, individual accounts cost $19 (one-time) and company accounts cost $99 (one-time). The fee was removed entirely. Source: Windows Developer Blog, 2026-05-07.

### 2.2 Submission steps for an MSIX-packaged desktop app

1. **Register a developer account** at `partner.microsoft.com`. Free; no fee as of 2026.
2. **Create an app submission** in Partner Center. Reserve the app name (this creates the identity).
3. **Build and package the app as MSIX.** For Tauri apps: the `.msix` file is generated during the build process. The package manifest (`AppxManifest.xml`) declares the app identity, capabilities, and the entry point.
4. **For MSIX/AppX packages:** you do NOT need to pre-sign with a CA-trusted certificate. The Store replaces any existing signature with a Microsoft certificate during publishing. Source: Microsoft Learn, "Get started with Microsoft Store", 2026-08-24.
5. **Upload the MSIX** to Partner Center.
6. **Complete the submission form:** pricing, age ratings, privacy policy URL, description, screenshots.
7. **Certification** — automated tests run against the package. Common failures: restricted capabilities without justification, version number format, crashes.
8. **Publishing** — after certification, the app becomes available in the Store. Users install via the Store client.

Source: Microsoft Learn, "Publish your first Windows app", 2026-08-29 (`https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/publish-first-app`).

#### For MSI/EXE installers submitted to the Store

If you submit an MSI or EXE installer (not MSIX), you must Authenticode-sign the installer yourself before submission. The Store does NOT re-sign MSI/EXE files. Source: Microsoft Learn, "App package requirements for MSIX app", 2026-07-16.

Tauri v2's Microsoft Store guide (`https://v2.tauri.app/distribute/microsoft-store/`) describes the NSIS `.exe` path for Store submission, using the silent install flag `/S` (uppercase S).

### 2.3 The sandbox constraint — the highest-risk unknown for Capybaras

**This is the most important section for the Capybaras architecture.**

An MSIX-packaged app can run at one of two trust levels:

| Level | `uap10:RuntimeBehavior` | Isolation | Can spawn child processes |
|---|---|---|---|
| **Full trust** | `packagedClassicApp` or `win32App` | Medium IL (same as standard desktop app). Filesystem and registry virtualization apply at the MSIX container level, but the process can access most system resources. | **Yes** — the app runs as a normal Win32 process and can spawn child processes freely. Sidecar executables work. |
| **AppContainer** | `AppContainer` | Strictly isolated. Process and children can only access explicitly granted resources. | **Restricted** — child processes inherit the AppContainer and must also be within the grant list. |

Source: Microsoft Learn, "MSIX containerization overview", 2026-04-15; Microsoft Learn, "Windows apps--packaging, deployment, and process", 2026-08-29.

**The key finding for Capybaras: most Win32 desktop apps packaged as MSIX use `packagedClassicApp` (full trust, Medium IL).** This is the default for apps converted from Win32 installers using the MSIX Packaging Tool, and for most WinUI 3 desktop apps. UWP apps use AppContainer. But a Tauri app packaged as MSIX would use `packagedClassicApp` because it is a Win32 desktop app, not a UWP app.

Capybaras' architecture is: Tauri shell (Rust, Win32) launches a Node sidecar as a child process, which opens a localhost TCP port for IPC and writes to user data directories. Under `packagedClassicApp`:

- **Process spawning: UNCONSTRAINED.** The Tauri process can spawn the Node sidecar binary.
- **Filesystem: virtualized but not blocked.** Writes to the install directory (`Program Files\WindowsApps`) are virtualized; writes to user-accessible paths (`%LOCALAPPDATA%`, `%APPDATA%`) go to real disk. This matches the Gateway's expected data patterns.
- **Network (localhost): UNCONSTRAINED.** The app can open localhost TCP ports. No AppContainer network isolation applies.
- **RunFullTrust capability:** If the app needs full system access, the `runFullTrust` restricted capability can be declared in the manifest. This is needed for some system tray interactions on older Windows builds.

**However, there are two unverified aspects:**

1. **MSIX filesystem virtualization for sidecar binaries.** The sidecar binary lives inside the package directory (`C:\Program Files\WindowsApps\Publisher.AppName\`). At runtime, MSIX makes this directory read-only from the app's perspective (writes virtualize). But the app CAN read and execute its own bundled binaries. The real question: can the sidecar binary itself write to `%LOCALAPPDATA%`? Yes, because child processes inherit the parent's token and run at the same integrity level. The virtualization applies at the process level; the child process sees the same virtualized view.
2. **The Gateway opens a TCP port on localhost and may need to register as a Windows Scheduled Task** (for restart on boot). MSIX packages have their own startup task mechanism (via `desktop:StartupTask` in the manifest) and do not support traditional Scheduled Tasks. The startup path would need to be implemented as an MSIX startup task, not a `schtasks`-registered task. This is a concrete design change.

**Recommendation for Phase 0:** Before committing to MSIX/Store as the primary path, build a throwaway Tauri app that launches a Node sidecar, writes to `%LOCALAPPDATA%`, and opens a localhost port — then package it as MSIX and test on a clean Windows VM. If sidecar spawning works and the localhost port is accessible, the architectural risk is retired. If not, pivot to MSI-only distribution.

### 2.4 Updates via the Store

Store-distributed apps are updated through the Store client automatically. The Tauri updater plugin must be disabled or removed for the Store build. Version management is done through Partner Center — upload a new MSIX with an incremented version number, and Store handles the rollout.

## 3. Azure Artifact Signing

### 3.1 Current pricing tiers

| Tier | Price | Signatures/month | Certificate profiles |
|---|---|---|---|
| **Basic** | $9.99/mo | 5,000 | 1 |
| **Premium** | $99.99/mo | 100,000 | 10 |

Pricing per Microsoft's official pricing page (`https://azure.microsoft.com/pricing/details/artifact-signing/`). Confirmed by multiple third-party sources (DevClass 2026-01-14, Melatonin 2026-06-19, ITWriting 2026-07-23).

### 3.2 Eligibility — the critical constraint

**Organizations (businesses):** USA, Canada, EU, and UK only.

**Individuals:** USA and Canada only.

Source: Microsoft Learn, "Code signing options for Windows app developers", 2026-08-29. Also confirmed by Melatonin blog (2026-06-19) which cites the Microsoft Security Blog GA announcement.

If the Capybaras publisher is an individual outside the US or Canada, Azure Artifact Signing is **not available**. The fallback is an OV certificate from a third-party CA ($150-$300/year).

### 3.3 Setup steps

Based on the Melatonin blog guide (2026-06-19) and Microsoft's official quickstart:

1. **Azure subscription required** — paid (pay-as-you-go or enterprise). Free, trial, and sponsored subscriptions are NOT supported. Source: Microsoft Learn FAQ, 2026-08-14.
2. **Create an Artifact Signing account** — search "Artifact Signing" in the Azure portal, select subscription, pick a region, and note the endpoint URL.
3. **Register `Microsoft.CodeSigning` resource provider** in the subscription.
4. **Create an App Registration** in Microsoft Entra ID for API credentials — note the `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, and create a `AZURE_CLIENT_SECRET`.
5. **Assign roles:** Identity Verifier to your Azure user, Certificate Profile Signer to the App Registration.
6. **Complete identity validation** — submit business/individual identity documents. Microsoft validates your legal entity name (this becomes the signing subject).
7. **Create a certificate profile** in the Artifact Signing account.
8. **Sign using the Azure SDK** or Tauri's built-in support (see section 3.4).

### 3.4 Tauri v2 integration

Tauri v2 supports Azure Artifact Signing directly in `tauri.conf.json`:

```json
{
  "bundle": {
    "windows": {
      "azureArtifactSigningEndpoint": "https://wus2v2.api.artifact-signing.azure.com"
    }
  }
}
```

The endpoint URL is the region-specific Artifact Signing endpoint. Tauri uses the `signtool` Azure Artifact Signing integration under the hood. Source: Tauri v2 docs, "Windows Code Signing", updated 2026-09-11.

### 3.5 SmartScreen reputation — the critical question

**Azure Artifact Signing does NOT provide instant SmartScreen trust.** This is stated explicitly in Microsoft's own documentation:

> "Azure Artifact Signing does not provide instant SmartScreen trust, but signing consecutive releases with a consistent publisher/signing identity lets publisher reputation build over time, so later releases can inherit trust."

Source: Microsoft Learn, "Code signing options for Windows app developers", 2026-08-29, comparison table.

There is a **conflict** with some third-party claims. The Melatonin blog (2026-06-19) states: "you always get instant reputation on all executables signed — that reputation is tied to your identity." However, the Microsoft Learn page is the authoritative source, and it explicitly contradicts this claim. **Trust Microsoft's documentation over third-party blog posts.**

Additionally, a Microsoft Q&A report (2026-07-22) documents that in 2026-03, Microsoft rotated the intermediate CA used by Artifact Signing. Established publishers saw SmartScreen warnings reappear because the new intermediate CA had no accumulated reputation. This confirms that even consistent publisher identity does not guarantee immunity.

**Practical impact for Capybaras:**
- If distributed outside the Store (MSI only via direct download), expect SmartScreen warnings on early releases.
- Warnings should diminish over weeks/months as clean download counts accumulate.
- The SmartScreen reputation system has no published SLA or threshold. Reports on Microsoft Q&A (2026-04-28) describe file submissions staying "In progress" for 13+ days with no published review timeline.

**The only way to guarantee no SmartScreen warning is to distribute through the Microsoft Store.** This finding reinforces the BUILD-PLAN.md recommendation: Store-first, MSI as a parallel channel.

### 3.6 Certificate lifecycle

Artifact Signing certificates are short-lived (3-day validity, renewed daily). The service rotates the leaf certificate automatically. The signing subject is determined by the identity validation and cannot be customized (no custom CN or O). Source: Microsoft Learn FAQ, 2026-05-14.

## 4. winget manifest submission

### 4.1 Accepted installer formats

winget accepts: EXE, MSI, MSIX, ZIP, Inno Setup, Nullsoft Scriptable Install System (NSIS), WiX Toolset (BURN), and portable executables. Script-based installers (batch, PowerShell) are not accepted.

Source: Microsoft Learn, "Submit your manifest to the repository", 2026-03-23; Windows Forum guide, 2025-11-22.

For Capybaras, the MSI (WiX) installer generated by Tauri is eligible.

### 4.2 Manifest structure

A winget manifest is three YAML files per package version, submitted as a pull request to `https://github.com/microsoft/winget-pkgs`:

- **Locale manifest** (`<package-id>.locale.<locale-code>.yaml`) — publisher display name, package name, description, license.
- **Version manifest** (`<package-id>.yaml`) — package identifier, publisher, version.
- **Installer manifest** (`<package-id>.installer.yaml`) — installer URL, SHA256 hash, architecture, installer type (`wix`), installer switches (silent: `-qn` for MSI, silentWithProgress: `-qb!`), product code, signature SHA256 (if signed).

### 4.3 Submission and review process

1. **Create manifests** — manually or using `wingetcreate` (`wingetcreate new --url <installer-url>`).
2. **Fork `microsoft/winget-pkgs`** and submit a PR with the manifests in `manifests/<publisher>/<package>/<version>/`.
3. **Automated validation:** PR bots check manifest format, SHA256 match against the installer URL, policy compliance, malware scan. Historically this was fully automated and merged in minutes.
4. **Manual review:** The validation process shifted toward more manual review after problems emerged. Merge times vary from hours to days. Source: Windows Forum, 2025-11-09; MSEndpointMgr, "Is WinGet Enterprise Ready?", 2026-08-01.
5. **PR merged:** The package becomes available via `winget install <package-id>` within 1-2 hours.
6. **Version bumps:** Each new release requires a new PR. Automate this with a CI workflow that uses `wingetcreate` to update manifests and opens the PR on release.

### 4.4 Signing requirement

winget does not require a signed installer to accept a manifest. However, an unsigned installer will trigger SmartScreen when a user actually downloads and runs it. Signing is strongly recommended to avoid friction.

If the MSI is signed, the installer manifest should include `SignedWithSignature` (the SHA256 fingerprint of the signing certificate) and `SignatureSha256` for validation.

## 5. Unverified claims

The following could not be authoritatively verified, either because no source exists, sources conflict, or the information does not exist in current documentation.

### 5.1 Node sidecar behavior in an MSIX full-trust package

**Unverified.** While the theory described in section 2.3 is sound — a `packagedClassicApp` runs at Medium IL and can spawn child processes — no public source could be found that specifically documents a Tauri + Node sidecar architecture inside an MSIX package for the Microsoft Store. The concept is a composite of:
- MSIX full-trust behaviour is documented (Microsoft Learn).
- Tauri sidecar spawning is documented (Tauri docs).
- Tauri + MSIX is documented (Tauri Microsoft Store guide).

But no source documents all three combined. **This should be verified with a throwaway prototype in Phase 2 (feasibility spike) of the build plan.**

### 5.2 MSIX startup task vs Windows Scheduled Task

**Unverified.** The Gateway currently installs via `schtasks` for auto-start. MSIX packages use a different mechanism (`desktop:StartupTask` in `AppxManifest.xml`). Whether the Gateway can be migrated to the MSIX startup model without losing functionality (e.g., running as the logged-in user, not a SYSTEM task) is not documented for this specific use case. The MSIX startup task runs at login and executes the packaged app automatically. It may or may not support the sidecar startup pattern required by Capybaras.

### 5.3 SmartScreen reputation timeline

**Unverified.** Microsoft publishes no SLA or specific threshold for how many downloads or what time period is needed to build SmartScreen reputation for a new publisher. The only documented fact is that it "accumulates over time." Community reports on Microsoft Q&A describe extended waits, but the sample size is small and undocumented. Expect weeks to months of warnings, not days.

### 5.4 Azure Artifact Signing instant reputation claim

**Unverified claim debunked.** The claim that Artifact Signing grants instant SmartScreen reputation appears in at least one third-party blog (Melatonin 2026-06-19) but is contradicted by Microsoft's official documentation (Microsoft Learn, "Code signing options", 2026-08-29). Since official documentation takes priority, the correct finding is: **Artifact Signing does NOT provide instant SmartScreen trust.**

### 5.5 Intermediate CA rotation and reputation loss

**Partially verified.** A Microsoft Q&A report (2026-07-22) documents SmartScreen warnings returning after the intermediate CA rotation in March 2026. This is a single user report, not a systematic study. The scale and frequency of this issue across all Artifact Signing customers is not documented.

## 6. Recommendation summary for Capybaras

| Decision | Recommendation | Rationale |
|---|---|---|
| **Primary distribution channel** | Microsoft Store (MSIX) | Resolves SmartScreen warning entirely. Free developer account as of 2026. Microsoft re-signs the package. |
| **Secondary distribution** | Signed MSI via direct download + winget | For power users, IT departments, and anyone who cannot use the Store. |
| **Code signing for MSI** | Azure Artifact Signing ($9.99/mo) if publisher is eligible (US/CA/EU/UK org or US/CA individual). Fallback: OV certificate ($150-300/yr). | Cheaper and cleaner than OV, but availability is gated. |
| **Updater for Store builds** | Disabled — let the Store handle it. | Store and Tauri updater conflict. |
| **Updater for MSI builds** | Tauri updater plugin with static JSON manifest. | Verified signature verification, no backend needed. |
| **Sidecar packaging** | Ship portable Node runtime binary, not pkg-compiled code. | OpenClaw Gateway has 65 deps + dynamic loading; pkg fails on dynamic graphs. Larger runtime is the correct tradeoff. |
| **Startup mechanism for Store build** | MSIX startup task (`desktop:StartupTask`) instead of `schtasks`. | Must be verified in Phase 2. |
| **Per-release automation** | GitHub Actions CI with Tauri's official GitHub pipeline (`https://v2.tauri.app/distribute/pipelines/github/`). | Signs, builds MSI/MSIX, optionally submits to winget-pkgs. |

### Cost summary

| Item | Annual cost |
|---|---|
| Microsoft Store developer account | **$0** (free since 2026) |
| Azure Artifact Signing Basic (if eligible) | ~$120/yr |
| OV certificate (fallback) | $150-$300/yr |
| GitHub hosting | $0 |
| Updated MSI signing each release | Included in Azure/OV cost |
| **Total (Store + Azure)** | **~$120/yr** |
| **Total (Store + OV)** | **$150-$300/yr** |

### Risk register for this phase

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| MSIX package blocks Node sidecar spawning | Medium | High — forces MSI-only distribution | Throwaway prototype in Phase 2 |
| MSIX startup task incompatible with Gateway lifecycle | Medium | Medium | Alternative: launch sidecar on app start (no auto-restart) |
| SmartScreen warnings persist >3 months on MSI path | Medium | Medium — damages first impression | Store path avoids this entirely |
| Artifact Signing unavailable for publisher | Medium (if individual outside US/CA) | High | Fallback to OV certificate from Sectigo or DigiCert |
| Azure subscription cost for Artifact Signing | Certain | Low | Minimum $9.99/mo even if zero releases that month |

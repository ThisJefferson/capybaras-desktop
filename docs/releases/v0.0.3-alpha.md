# v0.0.3-alpha — M3: the shell runs

**Milestone M3 complete.** The desktop shell exists, builds, and supervises a Node sidecar correctly on Windows. All seven steps of `docs/plans/M3-shell.md` are done and verified.

This is still pre-alpha: nothing here is a shippable app. What it is, is the hardest structural part of the product proven to work.

## What was built

`apps/desktop/` — a Tauri v2 shell:

| Part | Path |
|---|---|
| Rust shell | `src-tauri/` (`paths.rs`, `sidecar.rs`, `single_instance.rs`, `lib.rs`) |
| Node sidecar | `sidecar/sidecar.mjs` |
| Status frontend | `web/index.html` |
| Verification | `scripts/verify-supervision.ps1` |

The shell **imports** the risk classifier and policy layer rather than duplicating them. There is one source of truth for what a gate is.

## The two guarantees, both measured

**1. The sidecar cannot outlive the shell.** It is assigned to a Windows Job Object created with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, before the process is spawned, so there is no window in which it sits outside the job.

**Verified by hard-killing the shell from outside the agent's own process tree** — launched via a Scheduled Task, so the host runtime's own Job Object could not contaminate the result. This is the measurement Spike 001 could not take. Result: **zero orphans.**

**2. A graceful stop reaches the child.** The sidecar is asked to stop over stdin and given a bounded grace period; force is only the fallback. On Windows `Child::kill()` is `TerminateProcess` — it runs no handler in the child — so a passing test here is a real assertion, not a formality.

**Verified by test:** the sidecar's own shutdown handler logs, exits 0 on its own, and is never forced.

---

## Path resolution never consults the working directory

Spike 002 found that a packaged app launches with `cwd = C:\Windows\System32`. Any path resolved from the working directory fails quietly on a real install.

`paths.rs` resolves from the executable, an explicit environment override, or a compile-time constant. There is no `cwd`-relative fallback anywhere. **Verified by launching with `cwd = C:\Windows\System32`** — the sidecar still started and reported that exact working directory.

---

## Single instance: refusal, not duplication

A second launch **refuses and exits** rather than starting a second agent — enforced by an exclusively-opened lock file whose handle Windows releases when the process dies, including badly.

This is a safety property. Two agents sharing one state directory, one credential set and one sidecar port is the contention this project exists to prevent; the precedent is two local model servers on one machine fighting over the same GPU.

**Verified at runtime:** first instance ran with a heartbeating sidecar; second printed `Capybaras is already running (lock held at …)` and exited. One shell, one sidecar, both cleared.

## Known gaps, stated rather than hidden

- **A second launch exits rather than focusing the first window.** That was the plan's exit criterion for this step. Focusing needs an IPC channel that does not exist yet. The safety-critical half works; the convenience half is deferred. (`DECISIONS.md` D17)
- **The MSIX state-path question is still open.** Spike 002 showed MSIX silently virtualises AppData writes. Whether a chosen user-visible path survives that is a packaging-phase measurement. (`DECISIONS.md` D15)
- **In development the sidecar resolves to the Node on `PATH`**, because a debug build has no bundled `node.exe` beside the executable. The release bundle will place it there; the resolution order is unchanged.
- **The interface is not built.** `web/index.html` is a status panel, not the product. That is M4.
